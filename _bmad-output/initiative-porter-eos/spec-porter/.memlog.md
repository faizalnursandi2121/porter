- (direction) Companion split: ui-design.md stays adopted companion (layout patterns and locked visuals); FR catalog and business rules distilled into spec-authored companions; kernel holds capabilities at user-journey level
- (capability) CAP-1 Account and assignment administration: Supervisi/Administrator create all accounts (no self-registration, mandatory school placement for EOS, temporary password with forced change on first login), move/end EOS assignments with full history; one active assignment per EOS and one active EOS per school. Success: feature tests prove role-scoped access, 15-minute lockout after 5 consecutive failures, and assignment invariants on move/end.
- (capability) CAP-2 Attendance proof: EOS checks in and out each with one selfie and device GPS; server-applied permanent watermark (site, local time, coordinates+accuracy); times recorded per school timezone with UTC reference; double check-in prevented, check-out before check-in prevented, check-out gated on Submitted Daily Report, second check-out rejected, same local school day rule enforced. Success: feature tests for each critical rule including watermark file differs from original.
- (capability) CAP-3 Attendance history visibility: EOS sees own history only; Supervisi/Administrator/HR see per-EOS per-site history with period filter showing local times, status, location, selfie photos per FR-48. Success: RBAC test proves EOS isolation and HR cannot reach report/inventory photos.
- (capability) CAP-4 Daily Report lifecycle: Administrator-managed versioned template of 5 sections with conditional mandatory explanations and photo evidence; server-side drafts; submit issues permanent unique number CMX.WR.YYYYMM.SEQUENCE; same-day self revision increments counter; reopen by Supervisi/Administrator with mandatory reason triggers in-app notification. Success: tests for number allocation and format, section completeness validation, revision counting, reopen to Needs Revision with notification.
- (capability) CAP-5 Site inventory and consumables: EOS logs received goods with mandatory photo; item statuses in-use/spare/damaged/returned/lost with mandatory reason for damaged and lost; material stock movements in/out/usage rejected when balance would go negative; inventory bound to the school not the EOS; Supervisi/Administrator corrections. Success: tests prove negative-stock rejection with balance message, ownership survives EOS transfer, status changes audited.
- (capability) CAP-6 KPI dashboard and export: Supervisi/Administrator filter by combinable period, school, EOS; six KPI groups (attendance, report completeness, network health, environment, anomalies, inventory); server-side Excel and PDF export honoring active filters. Success: demonstration produces export matching active filter; empty filter state shows No data for this filter.
- (capability) CAP-7 Audit and photo access control: append-only audit log of all critical actions including every selfie/evidence photo access with actor, role, action, object, UTC+local time, before/after; Administrator-only audit view with period/actor/action filters; photos served only through authorized endpoint after role check. Success: tests prove unauthorized roles denied at photo endpoint, each access writes an audit row, app users cannot modify audit rows.
- (capability) CAP-8 Master site data: Administrator manages site name, address, coordinates, timezone WIB/WITA/WIT, primary and backup internet providers; deactivation never deletes history. Success: test proves deactivated site leaves active flows while its historical records stay viewable.
- (capability) CAP-9 PWA field experience: installable PWA (manifest, icon, splash, static-asset service worker), mobile-first large targets, attendance disabled with explicit message when offline, upload progress with double-submit prevention and retry that preserves captured selfie/GPS or report data. Success: with connectivity off the attendance action disables with the FR-6 message and a failed upload leaves captured data intact for Try Again.
- (capability) CAP-10 Local-time correctness: all timestamps stored UTC and displayed per site timezone with tz label across attendance, reports, dashboard, exports. Success: unit tests of the UTC-to-local conversion helper plus UI/export render site-local time with WIB/WITA/WIT label.
- (constraint) Stack locked: Laravel 13 + Inertia v3 + React 19 + shadcn/ui starter kit, session-cookie auth, server-side routing only (no separate REST API); 4 roles RBAC enforced server-side on every request; Administrator superset of Supervisi
- (constraint) All timestamps stored UTC; conversion to school timezone happens in application layer from site master data; every display shows tz label (FR-35)
- (constraint) Photos live in private storage outside public root; every photo view goes through an app endpoint that checks role per FR-48 then writes an audit-log row before streaming the file; no directly guessable URL ever exposes a photo
- (constraint) Audit log is append-only, written automatically on every critical action, never editable or deletable by application users
- (constraint) Watermark FR-5b is stamped server-side at receive time; original unwatermarked selfie need not be kept; watermark text carries site name, local timestamp, lat/lng with accuracy; bundle internal TTF font, do not rely on OS fonts
- (constraint) Report numbers CMX.WR.YYYYMM.SEQUENCE are issued only on successful submit, globally unique and never reused; sequence never resets, crosses 9999; drafts have no number; revision and reopen never change the number
- (constraint) Daily Report template changes apply to new reports only; each report stores a template snapshot; dashboard comparisons use only stable core fields (CPU/RAM, AP offline, temperature, speedtest)
- (constraint) Report photo rules FR-20a: JPG/JPEG, PNG, WebP, HEIC/HEIF, PDF (never for selfie); max 10 MB per file; max 5 photos per section; max 10 per report; exactly 1 selfie per check-in and 1 per check-out; uploads failing rules are rejected at upload with explicit reason
- (constraint) Validation mandatory on client and server; server rejects submit when any section empty or missing photo; server is source of truth
- (constraint) Material stock balance may never go negative: rejecting transactions must state the current balance
- (constraint) Critical business rules must have automated tests: double check-in, report gate before check-out, double check-out, number allocation, photo access rights (PRD Technical 14; task-list Notes)
- (constraint) Inventory is owned by the school, not the EOS; moving an EOS never moves inventory
- (constraint) UI follows ui-design.md locked decisions: launcher for all roles without sidebar, module nav in header (mobile Sheet), copy UI English via __(), status badge variants fixed, all lists carry verbatim FR empty states
- (constraint) Every list has an informative empty state and error state; dashboard must respond under 3 seconds for common filters; support 200+ sites growth in schema and indexes
- (constraint) Deployment GitHub to Dokploy without separate staging; daily automated backup with a tested restore procedure required before go-live
- (note) Non-goals (PRD Bukan Tujuan + decisions 1,4,5,7,9): no lateness/payroll computation or vendor attendance integration; no full offline mode or sync; no push notifications (in-app polling only); no procurement/purchasing; no automatic device monitoring (CPU/RAM/uptime manually entered by EOS); no native iOS/Android apps; no vendor contract/SLA management; no internal chat; no minimum-stock thresholds (dashboard shows lowest-stock recap only); no absence time-window enforcement (evidence only); no photo retention/purge policy (deferred until company policy exists); no warehouse data import (deferred until format known); no multi-EOS-per-site; no staging environment
- (assumption) Single national deployment covering all 200+ sites; site timezone is authoritative for local dates; no staging environment is acceptable because releases ship through Dokploy
